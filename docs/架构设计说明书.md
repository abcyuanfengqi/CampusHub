## 1. 引言

### 1.1 编写目的

本文档是 CampusHub 校园服务中心项目的软件体系架构设计说明书，依据课程大作业任务书要求，采用五视图方法对系统的逻辑结构、开发结构、运行行为、物理部署与关键场景进行完整描述，并给出架构决策记录（ADR）、质量属性分析与一致性追溯，用于指导开发实现、评审验证与课程答辩。

### 1.2 项目背景

校园内信息分散在多个渠道（社团招新靠海报、竞赛组队靠群聊、二手交易靠朋友圈、失物招领靠公告栏），存在信息孤岛、组织效率低、资源利用率不高等问题。CampusHub 以"大学生服务中心"定位，聚合社团、竞赛、活动、二手、失物、消息六大类校园信息，形成一体化的信息共享中心，服务学生与社团管理人员。

### 1.3 适用范围

本文档覆盖系统的功能范围（9 个业务模块）、技术选型、部署形态与运行机制。读者包括：课程评审教师、项目组开发人员、答辩评委。

### 1.4 术语定义

| 术语 | 说明 |
|---|---|
| 五视图 | 逻辑、开发、运行、物理、场景五种架构视角 |

## 2. 需求概述

### 2.1 角色定义

系统定义三种角色（RBAC）：

| 角色 | 标识 | 职责 |
|---|---|---|
| 管理员 | ADMIN | 审批社团、发布公告、用户管理、数据看板、活动全生命周期管理 |
| 学生 | STUDENT | 浏览/报名活动、加入社团、发布二手与失物信息、竞赛组队 |
| 社团负责人 | CLUB_LEADER | 创建/管理社团、发布社团动态、发起活动 |

### 2.2 功能模块（9 个）

| 编号 | 模块 | 核心功能 |
|---|---|---|
| M1 | 用户与权限 | 注册/登录（JWT）、个人资料、管理员用户管理 |
| M2 | 社团管理 | 创建（PENDING→审批）、成员加入/管理、社团动态 |
| M3 | 竞赛组队 | 竞赛发布（按日期自动流转）、建队/入队（满员控制） |
| M4 | 活动组织 | 活动状态机、报名（Redis 防超卖）、签到核销、定时推进 |
| M5 | 消息通知 | 站内信（未读/已读/全部已读）、校园公告、MQ 异步通知 |
| M6 | 二手闲置 | 发布（ON_SALE→RESERVED→SOLD）、下架、成交通知 |
| M7 | 失物招领 | 发布遗失/拾获、认领（CLAIMED）、结案（RESOLVED） |
| M8 | 文件管理 | 文件上传（本地目录 + 元数据落库） |
| M9 | 数据看板 | 每日统计（幂等）、管理员聚合看板 |

### 2.3 数据规模

数据库 campus_hub 共 **19 张表**：user、user_role、club、club_member、club_post、competition、competition_team、team_member、activity、activity_registration、activity_checkin、secondhand_item、lost_found、notification、announcement、file_info、stat_daily、sys_config（审计表 audit_log 计入）。详见 `docs/sql/init.sql` 与数据视图 D2。

### 2.4 核心状态机（5 个）

| 业务对象 | 状态机 |
|---|---|
| 社团 Club | PENDING → APPROVED / REJECTED；APPROVED → DISBANDED |
| 活动 Activity | DRAFT → PUBLISHED → REGISTERING → IN_PROGRESS → FINISHED；任意态 → CANCELLED |
| 二手 SecondhandItem | ON_SALE → RESERVED → SOLD；ON_SALE → OFF_SHELF |
| 失物 LostFound | PENDING → CLAIMED / RESOLVED |
| 竞赛 Competition | RECRUITING → FULL → FINISHED（按报名截止/赛期自动流转） |

## 3. 架构设计目标与约束

### 3.1 质量属性目标（QAS）

| 质量属性 | 目标 | 实现手段 |
|---|---|---|
| 性能 | 活动报名并发不超卖 | Redis INCR 原子计数 + DB 唯一键兜底 |
| 可用性 | 核心链路不因通知失败而中断 | RabbitMQ 异步解耦，通知失败不影响主流程 |
| 安全性 | 接口级鉴权、密码不可逆存储 | JWT + 拦截器 + @RequireRole 切面 + MD5 存储 |
| 可维护性 | 模块独立、结构一致 | 模块化分层（modules/*）、统一 Result 响应 |
| 可扩展性 | 新增模块成本低 | 公共层（鉴权/事件/异常）+ 模块生成 Skill |

### 3.2 约束条件

- 课程要求：五视图文档、ADR ≥ 8 条、代码 ≥ 4000 行、单元测试 ≥ 10 个、Git 提交 ≥ 25 次、AI-Skill 包 ≥ 3 个且使用 ≥ 5 次、演示视频 5-8 分钟
- 技术约束：Java 17 / Spring Boot 3.2 / Vue 3，运行环境为本地 Windows 开发机
- 部署约束：演示环境为单机本地部署，Docker 仅编排中间件

## 4. 五视图架构设计

### 4.1 逻辑视图

#### 4.1.1 L1 系统上下文

CampusHub 系统面向三类参与者：学生、社团负责人、管理员。系统依赖四个外部服务：MySQL（持久化）、Redis（计数缓存）、RabbitMQ（消息队列）、本地文件系统（上传文件）。参与者通过浏览器访问前端（Vue SPA），前端通过 REST API 调用后端。

```
[学生] → 浏览器 → CampusHub 前端(Vue3) → REST/JWT → CampusHub 后端(Spring Boot)
                                                          ├── MySQL 8.0
                                                          ├── Redis 7
                                                          ├── RabbitMQ 3.12
                                                          └── 本地文件系统 ./uploads
[社团负责人] → 浏览器 → 同上
[管理员] → 浏览器 → 同上
```

#### 4.1.2 L2 功能结构

按 9 大模块组织功能树：用户认证（注册/登录/资料）、社团管理（创建/审批/成员/动态）、竞赛组队（发布/建队/入队）、活动管理（发布/报名/签到/状态推进）、消息通知（站内信/公告）、二手交易（发布/预约/成交）、失物招领（发布/认领/结案）、文件管理（上传）、数据看板（统计）。

#### 4.1.3 L3 容器图（组件划分）

- **前端容器**：Vue 3 SPA（Element Plus），Vite 开发服务器，axios 请求封装
- **后端容器**：Spring Boot 单体应用，内部按分层组织：Controller（接口层）→ Service（业务层）→ Mapper（数据访问层）
- **中间件容器**：MySQL、Redis、RabbitMQ
- **公共组件**：JwtAuthInterceptor（认证）、RoleAspect（授权）、EventPublisher（事件）、Result（统一响应）

#### 4.1.4 L4 分层架构

```
┌─────────────────────────────────────────────┐
│ 表现层 (views/*.vue + router + api/*.js)     │
├─────────────────────────────────────────────┤
│ 接口层 (Controller: /api/xxx/**)             │
│   ├─ JwtAuthInterceptor (Token 校验)          │
│   └─ @RequireRole Aspect (角色校验)           │
├─────────────────────────────────────────────┤
│ 业务层 (Service: 状态机 + 规则校验)           │
│   ├─ EventPublisher → RabbitMQ               │
│   └─ StringRedisTemplate → Redis 计数        │
├─────────────────────────────────────────────┤
│ 数据访问层 (Mapper extends BaseMapper)        │
├─────────────────────────────────────────────┤
│ 基础设施 (MySQL / Redis / RabbitMQ / 文件系统)│
└─────────────────────────────────────────────┘
```

#### 4.1.5 L5 领域模型

核心实体与关系：User（1:N 社团成员 ClubMember、1:N 报名 ActivityRegistration、1:N 二手 SecondhandItem、1:N 失物 LostFound、1:N 通知 Notification）；Club（1:N ClubMember、1:N ClubPost）；Activity（1:N ActivityRegistration、1:N ActivityCheckin）；Competition（1:N CompetitionTeam，1:N TeamMember）。详见 D1 ER 图与领域模型类图。

#### 4.1.6 L6 核心接口

统一 REST 风格：`/api/{模块}`，统一返回 `Result{code,message,data}`，Bearer JWT。8 个关键接口见 `08-逻辑视图-L6核心接口定义.md`：登录、注册、创建活动、活动报名（并发控制核心）、活动签到、创建社团、发布二手、统计看板。

#### 4.1.7 L7 关键时序（活动报名）

```
学生 → ActivityController.register()
  1. UserContext 取当前用户
  2. 校验活动状态 = REGISTERING（否则 BusinessException）
  3. 校验未重复报名（uk_activity_user，selectCount）
  4. Redis INCR 名额计数（返回 > maxParticipants → DECR 回滚并拒绝）
  5. 插入报名记录（唯一键兜底）
  6. 回写 activity.current_participants
  7. EventPublisher 发布 REGISTRATION_EVENT（RabbitMQ）
  8. NotificationConsumer 消费 → 写站内通知
  → 返回 {code:200, data:{status:"REGISTERED"}}
```

### 4.2 开发视图

#### 4.2.1 代码结构（V1）

```
backend/src/main/java/com/campushub/
├── common/          # 公共层
│   ├── annotation/RequireRole.java
│   ├── aspect/RoleAspect.java
│   ├── event/DomainEvent.java + EventPublisher.java
│   ├── interceptor/JwtAuthInterceptor.java
│   ├── utils/UserContext.java
│   └── (Result / BusinessException / GlobalExceptionHandler)
├── config/          # WebConfig / RabbitConfig / MybatisPlusConfig / ScheduledTasks
└── modules/         # 9 个业务模块，每个含 entity/mapper/service/serviceImpl/controller
```

前端：`frontend/src/{api,views,layouts,router,utils,stores}`。

#### 4.2.2 模块依赖原则（V2-V4）

- 上层依赖下层，禁止反向依赖；模块间不直接互相调用，统一通过事件（RabbitMQ）或数据库交互
- 公共层对业务层只提供服务，不感知具体业务
- 分页能力依赖 MybatisPlusConfig 分页插件，未配置则 Page 接口不可用（实际开发中曾踩坑，已修复）

#### 4.2.3 开发规范（V5-V8）

- 所有接口返回 `Result`；异常统一由 `GlobalExceptionHandler` 处理为业务码
- 鉴权两层：拦截器校验 Token 有效性（白名单 `/auth/**`、`/system/**`、`/swagger`、`/file/**`），切面校验角色
- Service 层集中状态机校验；唯一键约束在数据库层 + 应用层双重保证
- 单测避免 LambdaUpdateWrapper（需 MyBatis-Plus 运行时缓存），改用字符串 UpdateWrapper

### 4.3 运行视图

#### 4.3.1 R1 认证流程

用户登录 → AuthController 校验密码（MD5 比对）→ 签发 JWT（2 小时）→ 前端存储 token → 后续请求携带 `Authorization: Bearer xxx` → JwtAuthInterceptor 解析校验并写入 UserContext（ThreadLocal）→ 请求结束清理。

#### 4.3.2 R2 RBAC 授权

请求进入后，AOP 切面检查方法上的 `@RequireRole("ADMIN")`，与 UserContext 中角色比对，不匹配返回 403。管理员接口示例：社团审批、公告发布、数据看板。

#### 4.3.3 R3 活动报名并发控制（Redis）

见 4.1.7 时序；核心是 Redis INCR 的原子性与 DB 唯一键的最终一致性兜底，二者保证并发下名额不超卖、一人一报。

#### 4.3.4 R4 异步消息链路

RabbitConfig 定义直连交换机 `campushub.exchange`、队列 `queue.campus.registration / club / trade`、死信队列 `queue.campus.dlx`。业务发布 DomainEvent（类型+payload），消费者按 routingKey 分流，写站内通知。内存事件幂等（已处理 key 集合）防止重复消费。

#### 4.3.5 R5 定时任务

ScheduledTasks：每分钟按时间推进活动状态（PUBLISHED→REGISTERING→IN_PROGRESS→FINISHED）与竞赛状态；每日 00:05 执行 stat_daily 统计（uk_date 幂等）。

#### 4.3.6 R6 文件上传

FileController 接收 MultipartFile → 写入 `./uploads`（application.yml 配置 `file.upload-dir`）→ 元数据（原名/大小/类型/路径）落库 → 返回访问路径。

#### 4.3.7 R7 数据看板

StatServiceImpl 每日聚合各表计数写入 stat_daily；看板接口（管理员）查询近 N 天趋势聚合返回。

### 4.4 物理视图

#### 4.4.1 P1 部署拓扑

单机部署：Windows 开发机运行 Spring Boot 应用（8080）、Vue 开发服务器（5173）、MySQL（3306）、Redis（6379）、RabbitMQ（5672）。前端 Vite 代理 `/api` → 8080。

#### 4.4.2 P4 Docker 编排

docker-compose.yml 编排 MySQL 8 / Redis 7 / RabbitMQ 3.12（management），含健康检查与数据卷，一键 `docker compose up -d` 拉起依赖。应用进程在宿主机运行（演示环境）。

### 4.5 场景视图

关键用户场景（对应需求用例）：
1. **学生报名活动**：浏览活动列表 → 查看详情 → 报名（名额充足则成功并收到站内通知）→ 活动当天签到
2. **社团负责人创建社团**：填写信息提交 → 状态 PENDING → 管理员审批通过 → 收到审批结果通知 → 发布动态
3. **二手交易**：卖家发布 → 买家预约（RESERVED）→ 卖家确认成交（SOLD）→ 双方收到通知
4. **失物招领**：发布拾获信息 → 失主看到并认领 → 管理员/发布人结案
5. **竞赛组队**：队长发布竞赛 → 报名期内建队 → 成员加入（满员 FULL）→ 赛期自动流转 FINISHED

## 6. 质量属性与一致性分析

### 6.1 性能

- 报名链路：Redis INCR 单次 O(1)，无锁竞争，支持高并发报名
- 列表查询：分页插件 + 索引（唯一键 uk_* 全部建索引）

### 6.2 安全

- 传输：JWT Bearer，Token 2 小时过期
- 存储：密码 MD5（不可逆），不存明文
- 接口：白名单 + 拦截器 + 角色切面三层防护；SQL 注入由 MyBatis-Plus 参数化预防

### 6.3 可用性

- 通知异步化：MQ 故障时主流程（报名/交易）不受影响，事件暂存内存
- 数据兜底：Redis 计数与 DB 唯一键双保险

### 6.4 可维护性

- 模块独立目录、统一命名（entity/mapper/service/serviceImpl/controller）
- 公共能力下沉 common/，新增模块用 Skill 批量生成

## 8. 架构一致性问题与权衡

### 8.1 问题一：单体应用的模块解耦边界

**描述**：9 个业务模块位于同一 Spring Boot 应用，模块间若直接调用会导致耦合。

**方案**：强制"模块间不直接调用"，跨模块协作统一走 RabbitMQ 事件（如活动报名→通知；社团审批→通知；二手成交→通知）。

**代价**：事件传递有轻微延迟（毫秒级），需要事件幂等与消费确认；换来模块独立可测试、可单独替换。

**验证**：单测中 mock 掉 EventPublisher，模块可独立测试（17 个用例通过）。

### 8.2 问题二：Redis 计数与数据库的一致性

**描述**：报名名额的 Redis 计数与 DB current_participants 可能短暂不一致（Redis 先增、DB 后写）。

**方案**：以 Redis 计数为准做准入判断，DB 唯一键做最终一致兜底；报名记录成功则回写 DB 计数，二者仅存在秒级窗口差异，且统计口径以 DB 为准。

**代价**：极端场景（Redis 重启丢失计数）下可能出现名额略超，由 DB 唯一键限制单用户重复报名兜底。

**验证**：ActivityServiceImplTest 覆盖"名额耗尽回滚计数"用例。

### 8.3 问题三：单体演进为微服务的预留

**描述**：当前为单体，未来若活动/消息流量增长需拆分。

**方案**：通过模块化边界 + 事件总线，未来可先拆"消息中心"（notify）为独立服务；公共层（JWT/事件）保持契约稳定。

**代价**：当前为演示环境，拆分收益不明显，保留 ADR-008 记录演进路径。
