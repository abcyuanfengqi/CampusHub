# CampusHub 校园服务中心 — 需求规格说明书

## 一、项目背景与痛点分析

### 1.1 选题背景

当前大学校园内信息高度分散：社团通知在QQ群、竞赛信息在各班班长、二手交易在朋友圈、失物招领在公告栏。学生需要在多个平台之间切换，信息获取成本高，且容易错过重要通知。

### 1.2 痛点调研

| 痛点 | 表现 | 影响 |
|------|------|------|
| 信息分散 | 社团/竞赛/活动/二手信息散落在10+个微信群、QQ群、朋友圈 | 学生每天刷群2小时+，仍错过重要信息 |
| 报名混乱 | 活动报名靠接龙，签到靠点名，统计靠Excel | 组织者效率低，学生不知道报没报上 |
| 交易不安全 | 二手交易靠朋友圈私聊，无担保无评价 | 容易遇到骗子，交易纠纷多 |
| 社团管理弱 | 社团成员管理靠Excel，活动通知靠群发 | 社长管理成本高，成员活跃度低 |

### 1.3 竞品分析

| 竞品 | 优势 | 不足 | 我们的差异化 |
|------|------|------|-------------|
| 超级课程表 | 课程表功能强 | 校园社交弱，二手交易差 | 专注校园服务，整合更多模块 |
| 今日校园 | 官方对接，功能全 | UI老旧，学生用户体验差 | 更轻量化，面向学生真实需求 |
| 闲鱼 | 二手交易成熟 | 不是校园场景，面对面交易难 | 校园场景，同校面对面，信用背书 |
| 微信群/QQ群 | 即时通讯 | 信息易淹没，无法检索 | 结构化信息，可搜索可追溯 |

## 二、角色定义

| 角色 | 描述 | 核心诉求 |
|------|------|----------|

## 三、功能需求清单（9大模块 × ≥3子功能）

### 模块1：用户权限模块
1. 用户注册（学号/手机号注册）
2. 用户登录（账号密码+JWT认证）
3. 个人信息管理（修改资料、头像、密码）
4. 角色权限控制（学生/社长/管理员）

### 模块2：社团管理模块
1. 社团创建与申请（提交材料，管理员审核）
2. 社团成员管理（审批入社、移除成员、角色分配）
3. 社团列表与搜索（按分类、热度、推荐）
4. 社团动态发布（社长发布活动/通知，成员可见）

### 模块3：竞赛组队模块
1. 竞赛信息发布（级别、时间、要求）
2. 队伍创建与招募（队长建队，发布招募要求）
3. 加入队伍申请（学生浏览队伍，申请加入，队长审批）
4. 队伍成员管理（队长管理队员，查看竞赛进度）

### 模块4：活动组织模块
1. 活动创建与发布（时间、地点、人数限制）
2. 活动在线报名（学生一键报名，名额递减）
3. 活动签到核销（二维码签到/手动签到）
4. 活动状态流转（草稿→发布→报名中→进行中→已结束）

### 模块5：信息推送模块
1. 系统公告发布（管理员发布全站公告）
2. 站内消息通知（活动提醒、审核结果、交易消息）
3. 消息已读/未读管理（未读数统计，批量已读）
4. 消息分类筛选（活动/社团/交易/系统）

### 模块6：二手闲置模块
1. 商品发布（标题、价格、图片、分类）
2. 商品浏览与搜索（分类、关键词、价格区间）
3. 商品状态流转（在售→预订→已售出）
4. 商品收藏与评论

### 模块7：失物招领模块
1. 失物/招领发布（类型、描述、地点、时间）
2. 认领申请（发布者审核认领人）
3. 状态流转（待认领→已认领→已解决）
4. 按地点/时间筛选

### 模块8：数据看板模块
1. 用户统计（总用户、日活、新增趋势）
2. 活动数据（活动数、参与率、热门活动）
3. 交易数据（二手成交量、热门分类）
4. 可视化图表（折线图、柱状图、饼图）

### 模块9：文件管理模块
1. 图片上传（活动封面、商品图、头像）
2. 文件存储（本地存储，URL返回）
3. 文件类型校验（jpg/png，大小限制）
4. 文件列表管理

## 四、核心状态机设计（C2复杂度）

### 4.1 活动报名状态机
```
DRAFT（草稿）→ PUBLISHED（已发布）→ REGISTERING（报名中）
→ IN_PROGRESS（进行中）→ FINISHED（已结束）
                ↘ CANCELLED（已取消）
```

### 4.2 社团审核状态机
```
PENDING（待审核）→ APPROVED（已通过）→ DISBANDED（已解散）
                ↘ REJECTED（已驳回）
```

### 4.3 二手商品状态机
```
ON_SALE（在售）→ RESERVED（已预订）→ SOLD（已售出）
              ↘ OFF_SHELF（已下架）
```

### 4.4 失物招领状态机
```
PENDING（待认领）→ CLAIMED（已认领）→ RESOLVED（已解决）
```

### 4.5 竞赛组队状态机
```
RECRUITING（招募中）→ FULL（已满员）→ REGISTERED（已报名）→ FINISHED（已完成）
```

## 五、非功能需求

### 5.1 性能需求
- 页面加载时间 ≤ 2秒
- API响应时间 ≤ 500ms（90%请求）
- 支持峰值QPS ≥ 100（活动报名瞬间）
- 数据库查询 ≤ 100ms（单表）

### 5.2 安全需求
- 密码MD5加盐哈希存储
- JWT Token有效期2小时，支持刷新
- 接口权限校验（未登录不能访问业务接口）
- SQL注入防护、XSS防护
- 敏感操作记录日志

### 5.3 可用性需求
- 系统可用性 ≥ 99%
- 支持7×24小时运行
- 数据库每日备份
- 关键操作有事务保障

### 5.4 可维护性需求
- 分层架构（Controller-Service-Mapper）
- 统一响应格式与全局异常处理
- 接口文档自动生成（Swagger）
- 代码规范：命名统一、注释完整

## 七、ER图概览

共19张表，核心实体关系：
- 用户 1:N 社团成员（一个用户可加入多个社团）
- 社团 1:N 活动（一个社团可办多个活动）
- 活动 1:N 活动报名（一个活动有多个报名者）
- 用户 1:N 二手商品（一个用户可发布多个商品）
- 竞赛 1:N 竞赛队伍（一个竞赛有多支队伍）
- 队伍 1:N 队伍成员（一个队伍有多个成员）
