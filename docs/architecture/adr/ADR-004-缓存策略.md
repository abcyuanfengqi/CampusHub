# ADR-004：缓存策略（Redis）

- 日期：2026-10-27
- 状态：已接受
- 涉及视图：数据 / 运行

## 背景

CampusHub 存在明显读多写少的热点数据：社团列表、二手商品列表、活动列表、系统公告、统计看板。需求要求 API 响应 ≤500ms、页面加载 ≤2s，峰值 QPS ≥100（活动报名瞬间）。需要引入缓存层避免数据库打满，同时支持登录验证码等临时数据。

约束条件：
- 缓存需支撑 C3 复杂度（异步消息）之外的 C2 状态机场景的并发控制（报名名额递减可用乐观锁，也可用 Redis 原子操作）
- 本地环境已安装 Redis 5.0（D:\tools\redis，端口 6379）
- 需满足非功能需求中"缓存穿透/击穿/雪崩"防护

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. Redis（单机） | 内存KV、性能极佳（10万+ QPS）、数据结构丰富（String/Hash/List/ZSet）、TTL过期、发布订阅；Spring Data Redis 集成成熟 | 单机无持久化高可用（本项目不需要）；内存有限（本项目数据 < 200MB 足够） |
| B. Caffeine（本地缓存） | 进程内、零网络开销 | 无法跨实例共享；本项目单实例虽可用，但验证码/分布式场景受限 |
| C. Memcached | 简单、成熟 | 数据结构单一（仅KV）、无持久化、无原子计数扩展；已逐渐被Redis取代 |
| D. 不引入缓存 | 架构最简单 | 热点数据全部打DB，无法满足 ≤500ms 与 QPS 100 要求 |

## 决策

**选择 A：Redis 5.0（单机，端口 6379），通过 Spring Data Redis（Lettuce）接入。**

缓存设计要点：
- **热点数据缓存**：社团列表 `club:list`、二手列表 `secondhand:list:page:{page}`、活动列表 `activity:list`，TTL 5~10 分钟，失效后回源 DB
- **验证码/临时数据**：`sms:code:{phone}`，TTL 5 分钟（预留扩展）
- **登录会话加速**：用户信息 `user:info:{id}`，TTL 2 小时（与 JWT 过期一致）
- **计数器**：活动报名人数 `activity:count:{id}`，用 INCR/DECR 原子操作防超卖（配合 DB 乐观锁双保险）
- **消息未读数**：`unread:{userId}`，Hash 结构按类型计数

## 理由

1. **性能达标**：Redis 读 QPS 远超需求（10万+），热点数据走缓存后 API 响应可稳定 <100ms；DB 压力下降 90%+。
2. **并发控制**：活动报名用 Redis INCR 原子扣减 + DB 乐观锁双保险，满足 C2 状态机与"峰值 QPS 100 不超卖"需求。
3. **生态契合**：Spring Data Redis + Lettuce 与 ADR-001（Spring Boot 3）无缝集成；Redis 与 RabbitMQ 同属常用中间件，运维统一。
4. **放弃的代价**：放弃 Caffeine（本地缓存）意味着热点数据有网络开销（局域网 <1ms，可忽略）；放弃 Memcached 因其数据结构弱、社区渐冷。
5. **复杂度控制**：缓存策略简单（Cache-Aside 旁路缓存：读缓存→未命中查DB→回填），不引入双写一致性复杂方案——业务对数据实时性要求低（5-10分钟可接受），避免过度设计。

## 影响

- **数据视图**：缓存键设计文档（D8 待第7周补）：Key 命名 `业务:类型:维度`，统一前缀防冲突
- **运行视图**：Redis 单实例进程，端口 6379，与 MySQL 同机（开发）/ 同 Compose 网络（生产）
- **质量属性**：性能（热点读 <100ms）、可用性（Redis 挂掉时熔断回源 DB，业务降级不中断）
- **防护措施**（第7周 D8 细化）：缓存穿透（空值缓存 + 布隆过滤器）、缓存击穿（互斥锁重建）、缓存雪崩（过期时间加随机抖动）
- **后续事项**：第10周起在社团/二手/活动模块接入；第12周看板统计用缓存聚合

## 验证方式

1. `redis-cli ping` 返回 PONG（✅ 已装 Redis 5.0）
2. 社团列表首次查询走 DB、二次命中缓存（第10周接口验证，打印缓存命中日志）
3. 活动报名 100 并发压测无超卖（第11周，Redis INCR + 乐观锁）
4. 缓存不可用（停 Redis）时系统降级可访问（第13周故障演练）
5. 数据量或并发超过单机 Redis 能力时，重新评估 Cluster 或读写分离
