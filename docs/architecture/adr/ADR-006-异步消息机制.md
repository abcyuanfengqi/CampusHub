# ADR-006：异步消息机制（RabbitMQ）

| 要素 | 内容 |
|------|------|
| **日期** | 2026-10-27 |
| **状态** | 已接受 |
| **涉及视图** | 逻辑视图 L3/L4/L7、运行视图 R1/R5、物理视图 P1 |
| **背景** | 系统需要在"活动报名、社团审批、二手成交"等事件发生时向用户发送站内通知。若在同步事务内写通知，会拉长事务、增加失败概率；要求满足 C4 复杂度（异步消息、事件驱动），并保证通知不丢失 |

## 备选方案

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| A. 同步调用写通知 | 业务事务内直接 insert notification | 实现最简单 | 事务变长、耦合、失败回滚业务 |
| B. 本地消息表 + 定时扫描 | 业务事务写消息表，定时任务转发 | 不依赖中间件 | 需轮询、复杂度高 |
| C. RabbitMQ 消息队列 | 事务提交后发布事件，消费者异步落库 | 解耦、削峰、可靠（持久化+ACK） | 需维护队列/死信 |
| D. Kafka | 高吞吐分布式消息 | 吞吐极高 | 重组件、个人项目过度设计 |

## 决策

采用 **方案 C：RabbitMQ 3.12**（本地安装，端口 5672），Direct 交换机 + 业务事件队列，事务提交后发布领域事件，消费者异步写站内消息；队列持久化 + 手动 ACK + 死信队列保证不丢消息。

## 理由

1. 消息量级（校园场景 DAU 数百、事件峰值 <100/秒）下 RabbitMQ 完全够用且运维简单，Kafka 属过度设计
2. 与 L7 时序图设计一致：报名事务提交 → 发布 `REGISTRATION_EVENT` → 消费者写 notification，主链路不阻塞
3. 已安装并配置环境（5672 端口），`spring-boot-starter-amqp` 依赖就绪，实现成本低
4. 解耦后：活动模块不依赖通知模块（V3 模块依赖图体现），满足"无循环依赖"

## 影响

- 消息定义：`REGISTRATION_EVENT`（活动报名）、`CLUB_APPROVED_EVENT`（社团审批）、`TRADE_EVENT`（二手成交）
- 消费失败策略：重试 3 次 → 进死信队列（`campushub.dlx`）人工排查
- 幂等：消费者按 `(eventId)` 去重，防重复通知（配合 R7 幂等设计）

## 验证方式

1. 报名活动 → RabbitMQ 管理页（15672）看到消息入队、消费者确认
2. 停掉消费者再报名 → 消息持久化不丢失，消费者恢复后补消费
3. 模拟消费失败 → 3 次重试后进死信队列
4. 同一事件重复投递 → 通知只写一条（幂等校验）
