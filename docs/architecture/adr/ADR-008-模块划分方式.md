# ADR-008：模块划分方式（按业务域分层分包）

| 要素 | 内容 |
|------|------|
| **日期** | 2026-10-27 |
| **状态** | 已接受 |
| **涉及视图** | 逻辑视图 L2/L4/L5、开发视图 V2/V3 |
| **背景** | 系统有 9 个一级业务模块 + 公共能力，代码结构需满足"模块划分清晰、无循环依赖、可维护"（架构设计 59 分权重），且后续要按模块并行开发与测试 |

## 备选方案

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| A. 按技术分层分包 | controller/service/mapper/entity 各一个大包 | 分层直观 | 业务边界模糊、模块难独立演进 |
| B. 按业务域分包（每模块自含分层） | `modules/{auth,user,club,...}`，各自含 controller/service/mapper/entity | 高内聚低耦合、模块可独立测试 | 公共代码需抽 common |
| C. 微服务拆分 | 每模块独立服务 | 隔离最强 | 个人项目运维成本过高 |

## 决策

采用 **方案 B：按业务域分包 + 公共层**，包结构：

```
com.campushub
├── CampusHubApplication.java
├── common/          # 公共层：Result、全局异常、JwtUtils、SecurityConfig、BaseEntity
└── modules/
    ├── auth/        # 登录注册（controller/service/mapper/entity）
    ├── user/        # 用户信息与角色
    ├── club/        # 社团管理
    ├── competition/ # 竞赛组队
    ├── activity/    # 活动组织
    ├── secondhand/  # 二手闲置
    ├── lostfound/   # 失物招领
    ├── notify/      # 消息推送
    └── stat/        # 数据看板
```

## 理由

1. 与需求文档 9 模块一一对应，L2 功能结构图/ L5 领域类图可直接映射到代码目录（V2 目录图验证）
2. 业务模块只依赖 common 层与数据库表，模块间通过 RabbitMQ 事件解耦（ADR-006），满足"无循环依赖"（V3 依赖图证明）
3. 个人开发时按模块迭代：先 auth/user（已实现）→ 再 club/activity → 依次推进，每模块独立可测
4. 若未来要拆分微服务，模块边界天然是服务边界

## 影响

- 每模块内固定四层：`controller`（接入）→ `service`（应用）→ `mapper`（基础设施）→ `entity`（领域），与 L4 分层架构一致
- 新增模块 = 新增一个 `modules/xxx` 包 + 路由前缀 `/api/xxx`，骨架化成本低
- 命名规范：`XxxController` / `XxxService` / `XxxMapper` / `Xxx`（实体）/ `XxxStatus`（状态枚举）

## 验证方式

1. `mvn compile` 通过且包依赖方向单一（依赖扫描脚本/IDE 依赖分析，无反向引用）
2. 每个模块路由前缀独立（`/api/auth`、`/api/club`、`/api/activity`...），Swagger 分组可见
3. 删除任一业务模块后系统仍可启动（公共层独立验证）
4. V3 模块依赖图与代码实际 import 关系一致
